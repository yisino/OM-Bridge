# ADR-0008: 禁止硬编码的可用性判断

## Status

Accepted（2026-09-12）—— 来源于一次真实故障

## Context

这是本项目里**代价最高**的一次踩坑，因此单独成篇。

上游 OpenMontage 的 `ComfyUIVideo` 工具有一个 `operation_statuses()` 方法，
它回答"t2v / i2v 这些操作现在能不能用"。它的实现方式是：**检查后端上是否存在
它内置支持的那几个 WAN 2.2 模型文件**，存在则 `AVAILABLE`，否则 `DEGRADED`。

而实际部署的机器上**没装 WAN，装的是 MiniMax H3**。结果：

```
ToolStatus.DEGRADED   （t2v / i2v 两个 operation）
```

于是发生了一连串的连锁反应：

1. Agent 的 preflight 读到 `DEGRADED`，判定"本地 GPU 路径不可用"；
2. Agent 转而路由到**收费的云端 provider**；
3. 用户看到的现象是"明明本地有一块 3080 和齐全的 H3 权重，为什么在用云服务？"

这个故障**不会报错**。它不会让任何测试失败，也不会打印任何异常——
它只是安静地把工作导流到了一条更贵、更慢的路上。

更深一层的原因是：`ComfyUIVideo` 的"可用性判断"把**具体模型清单**写死在了**通用工具**里。
当用户用自定义工作流接入一个它不认识的模型时，这个模型在它眼里等同于"不存在"。

修法是给上游打一个幂等的补丁（`>>> host-local H3` 标记包裹，便于上游 rebase 后重放），
新增 `_h3_local_models()`（支持 `COMFYUI_H3_LOCAL_MODELS` 环境变量覆盖，
逗号分隔），检测到任一 H3 扩散权重即视该 operation 可用。修复后：

```
ToolStatus.DEGRADED → AVAILABLE
```

## Decision

在新工程里把这条经验固化成**架构约束**：

> **可用性/就绪度的判断必须由"实现方声明"驱动，不能由"调用方硬编码"。**

具体落到本项目的结构上：

1. **资产需求是声明式的**：每个 `Solution` 通过 `AssetRequirement`
   （`role` / `category` / `name` / `modes` / `required` / `source_url`）声明自己需要什么。
   判断逻辑统一在 `core/assets.py` 的 `evaluate_assets()` / `readiness_by_mode()`，
   **不写在任何后端实现里**。

2. **逐模式报告**：`readiness_by_mode()` 返回 `{mode: {ready, missing}}`，
   而不是一个笼统的布尔值。因为"t2v 能跑但 ref2v 缺权重"是真实且常见的情况，
   用一个布尔值表达它必然导致误判（这也是"t2v 能跑却整体被判不可用"的成因）。

3. **声明可以被重新解释**：方案通过 `config_defaults()` 让"本机实际装了哪些权重"可由配置覆盖
   （`OMB_MINIMAX_H3_UNET` 等）。所以换权重不需要改代码，
   也就不会出现"代码里的清单与现实不符"。

4. **对外发布时把名单交出去**：`publish.py` 会把方案的 `preflight_models` 写成
   `COMFYUI_H3_LOCAL_MODELS` 变量放进上游的 `.env` 托管块，让上游也知道
   "本机其实有 H3"。

5. **区分"缺失"与"无法判定"**：`AssetStatus.declared` 表达"这一类根本没被报告"，
   与"报告了但里面没有"不同。把两者混起来会导致"去下载本来就有的权重"。

## Alternatives Considered

**选项 B：在后端实现里硬编码各方案的模型清单。**
这正是上游的做法，也正是故障来源。任何"新增模型要改后端代码"的设计，
都会在下一次接入新模型时重新触发同一个故障。不选。

**选项 C：不做就绪度判断，直接提交，失败了再说。**
省掉了误判风险，但把错误推到了最贵的位置：载荷已经进队列、模型可能已经开始换入换出。
而且失败信息（`POST /prompt` 400 / 渲染错误）比"缺哪个文件"难读得多。
更糟的是：Agent 拿到模糊失败后**仍然会去试云端**。不选。

**选项 D：把模型清单做成一个可配置的全局列表（单一 `AVAILABLE_MODELS` 变量）。**
比硬编码好，但仍是"一个扁平列表 + 全局判断"。它无法表达"哪个模式需要哪些权重"
（本项目的 ref2v 与 t2v 需要的扩散模型不同），也无法表达"某个模式还需要特定节点"。
粒度不够，会退回成笼统判断。不选。

**选项 E：只报告，不判断（把原始盘点结果丢给调用方自己判断）。**
把责任推给每个调用方，结果就是每个调用方各写一份判断逻辑——
`interfaces/` 三份、外部框架若干份，又回到"多份实现必然漂移"。不选。

## Consequences

**变容易的**：
- 接入新模型**不需要改任何后端代码**，因此不会再把新模型误判为不可用。
- "哪些模式能跑"的结论是**逐模式**的、可解释的（缺什么列什么，还带 `source_url`）。
- 声明可以随部署调整（配置覆盖），代码清单与现实不符的情况在结构上被消除。
- Agent 拿到的 `readiness` 足以做出正确决策（例如 ref2v 缺权重就退到 t2v），
  而不是"整体不可用 → 转投收费服务"。

**变难的 / 代价**：
- 每个新方案都要认真写 `asset_requirements()`（含节点）。这是额外工作量，
  但它是**唯一**能正确表达可用性的位置，省不掉。
- 声明需要与后端实际枚举到的命名完全一致（文件名/类名一个字符都不能差）。
  对不齐时的报错必须足够清楚——所以 `graph.bad_enum` 这类错误会**列出合法取值**。
- 资产盘点依赖后端能报告清单；后端部分不可用时只能得到 `declared=False`（"无法判定"），
  此时不能给出"就绪"的结论。

**后续要盯住的**：
- **任何时候想要写"如果是某后端/某模型就……"这种判断，先停下来**。
  这几乎总是意味着某个声明缺失了。
- code review 时重点看两处：`probe()` 里有没有把具体模型名单写进后端；
  `readiness` 有没有从"逐模式"退化成"一个总布尔值"。
- 上游 `>>> host-local H3` 补丁是**临时性**的（因为要改别人的仓库）。
  一旦上游支持了"由实现声明可用性"，应当把这个补丁撤掉，
  并在此 ADR 里记一笔 —— 长期带着一个猴子补丁是债务。
