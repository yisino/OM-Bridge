# ADR-0001: 双层扩展模型（Backend × Solution）

## Status

Accepted（2026-09-12）

## Context

需求原话是："当前对接 Comfy 的 Minimax-H3 只是其中一种实现，后续还会接入更多实现，
因此架构必须预留可扩展的多实现接入能力，实现之间解耦、便于新增与替换。"

这句话里的"实现"其实混着两种完全不同的变化，必须先拆开，否则抽象一定会做错：

| 会变的东西 | 例子 | 变化频率 |
|---|---|---|
| **执行引擎**——任务怎么提交、怎么查状态、产物怎么取 | ComfyUI，某云视频 API，本地子进程 | 低（年） |
| **模型语义**——图长什么样、有哪些参数、要哪些权重 | MiniMax H3、LTX-2、Wan 2.2 | 高（月） |

已有的现实约束：

1. 现在只有一个引擎（ComfyUI）+ 一个模型（H3）。**只有一个实例时做抽象，很容易过度设计。**
2. 但已有明确的第二个实例在路上（其他视频模型）。
3. 上游 OpenMontage 曾因为"可用性判断只认内置模型清单"而把可用的本地路径判为不可用
   （见 [ADR-0008](0008-avoid-hardcoded-readiness.md)），说明**抽象做错会有实际代价**，
   不是纯粹的"可维护性"问题。

## Decision

把"实现"拆成两层，各自独立扩展：

- **`Backend`（在哪跑）**：抽象"提交 / 轮询 / 取件"三阶段 + 可选的上传与预检，
  用 `Capability` 声明自己会什么。
- **`Solution`（用什么模型、怎么跑）**：抽象"图结构 + 参数集 + 资产需求 + 溯源"。
- 两者**只通过 `core/models.py` 的数据契约通信**（主要是 `JobSpec`），**互不 import**。
  一个 `Solution` 通过类属性 `backend_name` 声明自己跑在哪个后端上，
  且只依赖 `Backend` 的**抽象**，不依赖具体后端类。

核心不包含任何后端的实现代码。`core/` 里出现 `import om_bridge.backends.*` 即视为分层失效。

## Alternatives Considered

**选项 B：一层——"每个模型一个工具类"。**
最简单，短期最快。但会产生两种必然的坏情况：
两个模型跑在同一引擎上时，客户端代码、上传逻辑、轮询逻辑被复制两份（改一处忘一处）；
同一个模型要在两个引擎上跑时，模型逻辑被绑死在引擎实现里（无法复用）。
考虑到"模型会按月换、引擎会按年换"，这个复制是**必然发生**的，所以不选。

**选项 C：只抽象引擎，模型用配置文件描述（把图当数据写进 JSON/YAML）。**
诱人，因为"新增模型 = 加一个文件"。但图构造里有真实逻辑：约束校验、栅格吸附、
LoRA 与步数的配对、动态槽位的绑定顺序、不同模式的节点差异。
把这些塞进声明式文件会立刻需要表达式求值、条件分支、变量引用 —— 最终你会实现一门
残缺的编程语言（这是一个已知的失败模式）。不选。

**选项 D：让 `Solution` 直接依赖具体后端类。**
省掉一层的间接，但会让"同一模型换个引擎跑"需要改代码，与需求"便于替换"直接冲突。不选。

## Consequences

**变容易的**：
- 新增模型不动引擎代码；新增引擎不动模型代码。两个方向都是"新增目录"，不是"修改既有文件"。
- 引擎侧的上传/轮询/超时/缓存诊断逻辑**只有一份**，所有模型共享。
- 可以离线单测：`builder` 是纯函数，不需要后端在线。

**变难的 / 代价**：
- 多了一层间接。读代码时要先分清"这段属于哪一层"，新人上手成本变高。
  缓解：`backends/<engine>/` 与 `solutions/<name>/` 的目录结构强制体现了归属。
- 契约设计要提前想清楚（`JobSpec` 够不够表达？`Capability` 够不够用？）。
  设计不足时会出现"方案为了表达自己而反向依赖后端细节"。
- "只有一个实例"时这层抽象看起来像浪费 —— 需要靠本文档说明它为什么值得。

**后续要盯住的**：
- 如果出现**第三个引擎**，检查 `Backend` 抽象是否还成立；
  若某个引擎必须实现 `submit` 之外的东西才能工作，说明契约缺了一个概念（补 ADR）。
- 若某个方案被迫写 `if backend.name == "..."`，说明分层已经破了，要立刻停下来讨论，
  而不是"先这样以后再说"。
