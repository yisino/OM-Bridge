# ADR-0007: 日志只走 stderr

## Status

Accepted（2026-09-12）

## Context

三个交付面里，**MCP 使用 stdio 传输 JSON-RPC**。这意味着进程的 stdout 是**协议通道**，
不是给人看的输出。任何一行多余的输出（一个 `print()`、一条 warning、一个进度点）
都会导致客户端 JSON 解析失败。

而这个故障的**症状极具误导性**：客户端通常只报"JSON 解析错误"或"连接意外关闭"，
既不会指出是哪一行脏了 stdout，也不会指出是谁写进去的。历史上这类问题常常要靠
"二分注释掉 print"来定位。

同时，另外两个面对输出的需求是**相反的**：

- CLI 需要 stdout 输出**结果**（尤其是 `--json` 时，stdout 必须只有一份 JSON，
  才能 `| jq` 或 `| python -c`），进度提示不能混进去；
- MCP 的 stdout 完全被协议占用，结果要走 JSON-RPC 的 `result` 字段。

还有一个容易忽视的需求：**用户要看的进度**与**排查时才要的诊断**是两种东西。
如果把进度做成日志，那么调高日志级别（为了排查）反而会让用户看不到进度——
这在真实使用中很烦人。

## Decision

**所有非结果输出一律走 stderr。** 具体：

- `core/logging.py` 的 `configure_logging()` 强制 `propagate=False` 且 handler 指向 stderr，
  避免被宿主进程的 root logger 配置劫持（否则日志可能被重定向到 stdout）。
- 提供两个**语义分离**的通道：

  | 函数 | 面向 | 是否受日志级别影响 |
  |---|---|---|
  | `progress(msg)` | 人（运行状态） | **否**，总是输出 |
  | `diagnostic(logger, msg, ...)` | 排查者 | 是 |

- CLI 的 `--json` 模式下，**stdout 只有一份 JSON 文档**；
  进度与诊断全部在 stderr。`graph -o -` 会独占 stdout，因此不允许与 `--json` 同用。
- 结果（产物路径、结构化数据）走 stdout 或 JSON-RPC `result`，不走日志。

## Alternatives Considered

**选项 B：继续用 `print()`，靠 code review 保证不写到 stdout。**
没有任何强制力。这类错误会稳定地随时间的推移重新出现（新贡献者不会知道这个约束），
而且每次的排查成本都很高。不选。

**选项 C：用 `logging` 统一，把进度也做成一条日志记录（如 `logger.progress`）。**
会重新引入"调高日志级别后用户看不到进度"的问题。而"调试时反而丢失状态信息"
正是最让人困惑的场景。不选。

**选项 D：MCP 进程启动时把 `sys.stdout` 重定向到 stderr，只保留一个专用 fd 发协议。**
技术上可行，但会让"谁在写 stdout"变成隐式行为，且需要处理 fd 复制、缓冲、编码等问题。
用一个隐式重定向去掩盖纪律问题，不如把纪律写进代码（两个显式函数）。不选。

**选项 E：不做日志，只返回结构化结果。**
对 Agent 场景可行（错误信息在 `Issue.hint` 里），但人会失去"它在干什么"的感知，
长任务（本项目里一次生成可达 100s 以上）会让人怀疑进程死了。不选。

## Consequences

**变容易的**：
- MCP 的 stdout 天然干净：**没有任何函数会把日志写到 stdout**，不是靠约定而是靠实现。
- CLI 的 `--json` 可以安全地接管道。
- 调试时可以放心把日志级别调到 DEBUG：进度仍然可见（因为它不看级别）。
- `2>/dev/null` 与 `--json` 的组合语义清晰：静默日志、保留结果。

**变难的 / 代价**：
- 用户需要知道"日志在 stderr"，才能用 `2>&1` 看到进度；文档里必须写明。
- 所有代码必须用 `progress()` / `diagnostic()`，**不能用 `print()`**。
  这是一个需要靠检查清单与 code review 维持的纪律（`interfaces/mcp.py` 的模块文档
  与 `core/logging.py` 都写了这条警告）。
- 进度与诊断分离意味着"想同时看到两者"时要合并两个流，略麻烦。

**后续要盯住的**：
- 引入任何第三方库时，检查它是否**默认往 stdout 写**（很多库的进度条会）。
  这是最可能破坏本决策的途径。
- MCP 的 `stdout` 洁净性应当**可自动验证**：`scripts/mcp-smoke.py` 已经在做这件事
  （喂一条 `initialize`，检查输出是否是合法 JSON）。新增功能后请保持它通过。
- 若将来出现一个新的 stdio 类传输（如 LSP），同一条约束直接适用，无需重新讨论。
